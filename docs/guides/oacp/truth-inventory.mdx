This inventory is based on the Grantex C6Z authority route, the OACP artifact signer, verifier, key store, status list and artifact store, mandates, the ledger routes, the protocol surfaces, and tests in `apps/auth-service`, as merged to `main` and deployed on 2026-10-20 ([status](./runtime-launch-closure-prd#status-on-2026-10-20)).

## Truth Table

| Category | Grantex reality | Owner/action |
| --- | --- | --- |
| Implemented runtime | C6Z authority endpoint under commerce auth; allowlisted AgenticOrg service-token access; artifact issuance signed with an ES256 detached JWS over the RFC 8785 envelope by a DB-backed OACP issuer key published in `/.well-known/jwks.json`; persistence of every issue and refusal (`oacp_artifacts`); replay, read and revoke routes; an OACP Token Status List entry on every artifact and a signed `revocation` artifact on revoke; artifact safety checks; TTL; adapter mapping payloads; Intent, Cart and Payment mandates as ES256 JWTs (AP2-mapped claims, on the OACP Token Status List, revocable with their descendants, every refusal recorded) with presence and `amr` from the Commerce Passport and a passkey assertion over the cart's `checkout_hash` for `human_present` carts; suspension and reinstatement of artifacts and mandates; arbiter decision ledger with machine-profile decision grants, audit witness checkpoints and the wallet ledger hash chain; UCP business profile, ACP delegate-payment allowance and order events, `@grantex/mcp-auth` identity-linking scopes; x402 / MPP settlement receipts as signed `commitment_evidence`; profile-driven agent request signatures; the POS handoff boundary in policy and protocol artifacts (no POS evidence reaches Grantex today, so `mandate_capability` says `offline_pos_evidence_status: "unverified"`). Before this, the signature was a template string checked by string equality; that code is deleted. AgenticOrg owns implemented tenant/merchant/seller scoped commerce config and Shopify runtime sync. | Grantex keeps tests and guard scans current. |
| Implemented in source, not released | OACP artifact and mandate verifiers in the TypeScript, Python and Go SDKs, the `oacp` conformance suite, `@grantex/agent-httpsig` profiles, the `@grantex/x402` receipt helpers, the `@grantex/mpp` Payment scheme, and `@grantex/mcp-auth` commerce scopes. | Release through the normal package process; until then, build from the repository. |
| Implemented docs only | Historical Commerce V1 PRDs, launch plans, C6 review reports, and publication drafts. | Mark as historical where they conflict with this architecture. |
| Implemented but not broad launch | Commerce V1 payment-control pilot code and Plural sandbox/UAT-compatible adapter paths exist separately from the AgenticOrg OACP runtime split. | Keep separate from OACP authority docs. |
| Requires credentials or approval | `COMMERCE_C6Z_AUTHORITY_SERVICE_TOKEN`, `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS`, the first OACP issuer key (`POST /v1/commerce/oacp/issuer-keys/rotate`; none exists in production on 2026-10-20), `OACP_PUBLIC_DISCOVERY_ISSUANCE_ENABLED=true` before any merchant's public discovery can be issued enabled, `OACP_STATUS_LIST_PUBLIC_ENABLED=true` for relying-party status checks (off in production on 2026-10-20), `HTTP_SIGNATURE_DIRECTORY_ENABLED`, `REGISTRY_SCHEME_AGENT_IDS_ENABLED` and `AGENT_PASSPORT_KYA_TIER_ENABLED` (all off by default), merchant/AgenticOrg tenant approval, production key custody, provider or bank rail approval, POS callback approval, and external channel approvals. | Ops owner must collect evidence before public claims. |
| Missing | Public standards approval, broad external protocol partner program, universal buyer-surface rollout, live non-Shopify source adapters, live bank/custom provider adapters, live POS provider approval, and order/payment/POS execution through OACP artifacts (mandates authorise; the provider executes). SD-JWT VC mandates (AP2 v0.2) and a buyer-signed Trusted Surface are not implemented. Grantex writes no `commerce_orders` rows and sends no outbound ACP webhooks. Per-key signatures on the registry key directory need agent-held keys and are not implemented (the registry countersigns). | Treat as pending runtime/product gaps. |
| Stale/confusing docs | Older copy that says Grantex is the merchant connector runtime or payment-control loop for every buyer interaction. | Supersede with OACP authority docs and link here. |

| Gap | Owner | Action |
| --- | --- | --- |
| External protocol approval | Grantex + partners | Create a public partner review process and evidence checklist before making official status claims. |
| Production turn-on | Grantex operator + owner | Create the first OACP issuer key, then turn on `OACP_STATUS_LIST_PUBLIC_ENABLED`, in that order ([runbook](./operator-runbook#production-turn-on-order)). |
| AgenticOrg production tenant rollout | AgenticOrg + Grantex | After the turn-on: allowlist tenant, rotate service token, verify source evidence intake, and run authority request smoke. AgenticOrg's arbiter, ledger, protocol surfaces and mandate client are still in review in AgenticOrg. |

| Provider or bank rail execution | Pine Labs Plural/P3P, banks, fintech/custom providers + merchant + AgenticOrg | Complete provider-owned approval, webhook, rollback, and human review path. Grantex stores only non-sensitive evidence refs where needed. |
| Buyer-surface approvals | AgenticOrg + channel owners | Verify WhatsApp, Telegram, MCP, OpenAPI, A2A, and web policies before public launch. |
