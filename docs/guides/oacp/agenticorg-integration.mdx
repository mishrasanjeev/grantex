Canonical end-to-end flow: [OACP authority overview](./overview).

AgenticOrg calls Grantex only when it needs authority artifacts or verification. It does not route every buyer message through Grantex.

## Runtime Flow

```mermaid
sequenceDiagram
  participant M as Merchant
  participant A as AgenticOrg
  participant G as Grantex
  M->>A: Save merchant config and create Seller Commerce Agent
  A->>A: Store source/channel/provider/POS refs
  A->>A: Read-only Shopify sync and redacted evidence
  A->>G: POST /v1/commerce/oacp/c6z/authority-requests
  G-->>A: ES256-signed OACP artifacts or blockers
  A->>A: Verify each JWS (JWKS) and status list entry
  A->>A: Cache verified artifacts by tenant, merchant, seller, buyer scope
  A->>A: Prepare purchase or Offline POS handoff without execution
  A-->>M: Runtime ready, refresh needed, or blocker
```

## Request Contract

AgenticOrg sends:

- tenant, merchant, seller agent, and source identifiers;
- merchant self-service config refs for source connector, buyer channels, provider-owned payment rails, public publishing, and POS metadata;
- requested OACP artifact families;
- source observed timestamp;
- public-safe connector evidence;
- no raw Shopify credential, raw provider payload, checkout URL, or payment URL.
- no raw POS payload, raw payment payload, order-created claim, or POS paid-state claim.

Grantex returns:

- `201 artifact_issuance_ready` with artifact families when ready;
- `202 received` when connector evidence is still required;
- `422` when the request is private, stale, executable, or otherwise unsafe.

Every refusal is recorded in Grantex (`refusal_record_id`); a `202 received` intake is not.

## Verifying Artifacts

AgenticOrg must verify every artifact before caching it, as
[OACP artifact authority](./artifact-authority) describes:

- pin the Grantex issuer (`JWT_ISSUER`) and JWKS URI (`<issuer>/.well-known/jwks.json`) in
  configuration; never follow a URL taken from an artifact;
- run the eight verification steps with the refusal codes listed there (the shared vectors in
  `spec/examples/oacp/oacp-artifact-jws-v1.json` cover steps 1-6);
- read the status list at `status.status_list.uri`, verify it against the same JWKS, cache it no
  longer than its `ttl` (30 s), and refuse with `revocation_status_unavailable` when it cannot be
  read;
- treat `schema_version` `oacp.artifact.v1` as the signed profile, and artifact ids as unique per
  issuance (`oacp_art_<ULID>`), not stable per family.

Recovery after a cache loss uses replay: `GET /v1/commerce/oacp/artifacts?tenant_id=...` with the
same service token, following `next_cursor`. Revocation uses
`POST /v1/commerce/oacp/artifacts/:artifactId/revoke`.

## Public Catalog Publishing Boundary

AgenticOrg publishes public buyer-safe seller and product surfaces after it has valid Shopify/OACP evidence and the operator enables public catalog publishing. Grantex does not host these catalog pages and does not sit in the hot path for non-binding buyer questions.

Expected AgenticOrg public surfaces:

| Surface | AgenticOrg route |
| --- | --- |
| Seller profile page | `GET /api/v1/public/commerce/sellers/{merchant_id}?tenant_id=...&seller_agent_id=...` |
| Buyer-safe catalog JSON | `GET /api/v1/public/commerce/sellers/{merchant_id}/catalog.json?tenant_id=...&seller_agent_id=...` |
| Product detail page | `GET /api/v1/public/commerce/sellers/{merchant_id}/products/{product_slug}?tenant_id=...&seller_agent_id=...` |
| Product detail JSON | `GET /api/v1/public/commerce/sellers/{merchant_id}/products/{product_slug}.json?tenant_id=...&seller_agent_id=...` |
| Schema.org JSON-LD | `GET /api/v1/public/commerce/sellers/{merchant_id}/schema-org.jsonld?tenant_id=...&seller_agent_id=...` |
| Sitemap | `GET /api/v1/public/commerce/sellers/{merchant_id}/sitemap.xml?tenant_id=...&seller_agent_id=...` |
| llms.txt | `GET /api/v1/public/commerce/sellers/{merchant_id}/llms.txt?tenant_id=...&seller_agent_id=...` |

Those outputs must include source and freshness labels, must not expose Shopify credentials or raw provider payloads, and must not claim checkout, payment, mandate, order, certification, or external platform approval. If the AgenticOrg cache is stale, revoked, or source-mismatched, the public surface must block or label the missing requirement instead of inventing facts.

## Failure Handling

If Grantex is unavailable, AgenticOrg may answer non-binding buyer questions from valid cached artifacts. Commitment-bound or POS-bound requests must refresh, prepare no execution, use only valid cached policy when risk permits, or refuse.

## Arbiter Decisions

AgenticOrg's policy arbiter is authoritative and deterministic: it seals `allow` or `refuse` from the mandate, consent, Commerce Passport cap and OACP artifact evidence, and never waits for a person. It posts every sealed decision to Grantex, which only records and countersigns it.

`POST /v1/commerce/oacp/arbiter-decisions` uses the same service token and tenant allowlist as the authority route; developer, merchant and agent credentials are refused. The body:

```json
{
  "decision_id": "arb_dec_0001",
  "tenant_id": "cten_example",
  "merchant_id": "mch_example",
  "seller_agent_id": "seller-01",
  "buyer_agent_id": "shopper-01",
  "action": "purchase_handoff",
  "action_hash": "<lowercase hex SHA-256 of the RFC 8785 handoff payload>",
  "outcome": "allow",
  "rules_evaluated": ["mandate_present", "consent_granted", "passport_cap"],
  "failing_rule": null,
  "evidence": {
    "mandate_ref": "mandate:01", "mandate_hash": "<hex>", "consent_ref": "consent:01",
    "consent_status": "granted", "passport_ref": "passport:01", "artifact_ids": ["oacp_art_01"]
  },
  "decided_at": "2026-10-19T10:00:00Z",
  "policy_version": "2026-10-01"
}
```

| Outcome | Answer |
| --- | --- |
| `allow` (`failing_rule: null`) | `201 {decision_id, outcome, decision_grant, jti, exp, expires_at}`. `decision_grant` is a `decision+jwt` in the machine profile (`approver_auth: "policy_arbiter"`, `amr` from the evidence, no `acr`, `dwell_ms: 0`, `action_hash`, `decision_request` = `decision_id`, `sub` = `buyer_agent_id`), at most ten minutes long, signed with the platform key published at `/.well-known/jwks.json`. `exp` is seconds since the epoch. |
| `refuse` (`failing_rule` names one of `rules_evaluated`) | `201 {decision_id, outcome, recorded: true}`. Nothing is minted. |
| Same `decision_id`, same body | `200` with the first answer (same `jti` and `exp`). |
| Same `decision_id`, different body | `409 arbiter_decision_conflict`. |
| Malformed, an `allow` with no evidence, `decided_at` in the future, or an `allow` older than ten minutes | `422`; not stored. |

AgenticOrg verifies the returned `decision_grant` against the Grantex JWKS (`typ` `decision+jwt`, `aud` `urn:grantex:decision`, `approver_auth` `policy_arbiter`, `action_hash` equal to its own `payload_hash`) before storing the `jti` beside its decision row. Grantex's human decision-grant verifiers (`POST /v1/decisions/consume`, SDK `verifyDecisionGrant(s)` and `enforce()`) refuse a `policy_arbiter` grant, so it can never stand in for a human approval. The profile is specified in `spec/decision-grant.md` section 10.

## Witness Checkpoints

AgenticOrg anchors the head of its hash-chained `audit_log` and asks Grantex to witness it, so a later rewrite below a witnessed head is provable outside AgenticOrg.

`POST /v1/audit/witness-checkpoints` (same AgenticOrg service token) takes `{source: "agenticorg", tenant_ref, chain: "audit_log", head_seq, head_hash, anchored_at}` (`head_hash` lowercase hex SHA-256) and answers `201 {witness_id, countersignature, witnessed_at, created: true}`. `countersignature` is a compact JWS (`typ` `audit-witness+jwt`, platform key, `kid` in `/.well-known/jwks.json`) over those fields plus `witnessed_at`, with `jti` = `witness_id` and no `exp`.

| Case | Answer |
| --- | --- |
| Same `(source, tenant_ref, chain, head_seq, head_hash)` again | `200` with the stored witness and countersignature (`created: false`). |
| A different `head_hash` for a witnessed `(source, tenant_ref, chain, head_seq)` | `409 WITNESS_FORK`; `fork` holds the witnessed checkpoint (with its countersignature) and the presented hash. The attempt is recorded. |
| Malformed, or `anchored_at` more than five minutes ahead | `400`. |

`GET /v1/audit/witness-checkpoints?source=agenticorg&tenant_ref=...&limit=...` returns `{checkpoints, forks}`, newest `head_seq` first. AgenticOrg verifies the countersignature against the Grantex JWKS before storing the `witness_id` beside its anchor row, and treats a `WITNESS_FORK` as an irregularity of its own chain.

## Mandates

Grantex issues Intent, Cart and Payment mandates as ES256 JWTs signed with the OACP issuer key. Each mandate is on the OACP Token Status List. Why plain JWTs, and how they map to AP2: [OACP mandates decision](./mandates-decision). Each route takes the service token with its own route scope and the tenant allowlist, or an operator of the tenant. `tenant_id` is the Commerce Passport's commerce tenant.

| AgenticOrg needs | Call | Route scope |
| --- | --- | --- |
| An Intent mandate | `POST /v1/commerce/oacp/mandates/intent` with `{tenant_id, passport_jwt, description, max_amount: {value, currency}, merchants?, expires_at?, presence?}` | `commerce.oacp.mandates.intent.issue` |
| A Cart mandate | `POST /v1/commerce/oacp/mandates/cart` with `{tenant_id, passport_jwt, intent_mandate, checkout, presence?, webauthn_assertion?}`. `checkout` is the UCP checkout object (`id`, `currency`, `line_items[{id, quantity, ...}]`, `totals` with exactly one `total`). For `human_present`, `webauthn_assertion` is the buyer's WebAuthn `AuthenticationResponseJSON` whose challenge is `checkout_hash` = b64url SHA-256 of the RFC 8785 checkout. | `commerce.oacp.mandates.cart.issue` |
| A Payment mandate | `POST /v1/commerce/oacp/mandates/payment` with `{tenant_id, passport_jwt, cart_mandate, rail: "plural" \| "upi_autopay" \| "card_network_token", token_binding: {type, id}}`. Never send card data. | `commerce.oacp.mandates.payment.issue` |
| A server-side check | `POST /v1/commerce/oacp/mandates/verify` with `{tenant_id, mandate, expected_type?, expected_merchant_id?}` returns `{valid, refusal_code, mandate_type, mandate_hash, claims}` | `commerce.oacp.mandates.verify` |
| Revocation | `POST /v1/commerce/oacp/mandates/{jti}/revoke` with `{reason_code?}` revokes the mandate and every mandate issued under it (201, or 200 when already revoked) | `commerce.oacp.mandates.revoke` |

An issue response is `{mandate, jti, mandate_type, exp, status: {status_list: {idx, uri}}, mandate_hash, claims}`. Store `jti` and `mandate_hash` (lowercase hex SHA-256 of the compact JWT) in the ledger and in the arbiter evidence (`mandate_ref`, `mandate_hash`). Put the three mandate hashes in the Plural order metadata.

Verify every mandate locally before relying on it. Use the pinned Grantex issuer and JWKS, and check the status list. Order and refusal codes:

- `mandate_malformed`, `mandate_algorithm_unsupported`, `mandate_type_mismatch` (check the expected `typ`);
- `issuer_key_untrusted`, `mandate_signature_invalid`, `mandate_issuer_mismatch`, `mandate_claims_invalid`;
- `mandate_not_yet_valid` (60 s skew), `mandate_expired`, `mandate_lifetime_exceeded` (`exp - iat` over 600 s);
- `mandate_audience_mismatch` (`aud` is the merchant id);
- `mandate_revoked`, `mandate_suspended`, `revocation_status_unavailable` (fail closed).

Then check the chain:

- the cart's `intent_mandate_jti` and the payment's `cart_mandate_jti`;
- `payment.transaction_id == cart.checkout_hash`;
- the payment amount and currency equal the cart total;
- the cart total is within the intent cap;
- the same tenant, merchant, `sub`, buyer agent and `consent_ref`.

A failed chain check is `mandate_chain_mismatch`. `@grantex/sdk` ships this as `verifyOacpMandate` and `checkOacpMandateChain`, and the shared vectors are in `spec/examples/oacp/oacp-mandates-v1.json`.

Issuance refuses, and records the refusal (the error `details.refusal_record_id`), with these codes:

- passport and consent: `passport_invalid`, `passport_revoked`, `passport_not_checkout`, `passport_scope_missing`, `passport_cap_missing`, `consent_not_active`, `passport_cap_exceeded`, `currency_mismatch`, `merchant_not_allowed`;
- presence: `presence_mismatch` (a `human_not_present` mandate under a `human_present` consent or parent);
- parent mandate: `parent_mandate_expired`, `parent_mandate_revoked`, `parent_mandate_invalid`, `mandate_chain_mismatch`, `intent_cap_exceeded`;
- passkey: `passkey_evidence_required` (a `human_present` cart without an assertion), `passkey_evidence_invalid`, `passkey_evidence_replayed`;
- request content: `checkout_invalid`, `card_data_refused`, `payment_rail_unsupported`, `token_binding_invalid`, `intent_invalid`.

If revocation state is unavailable, the response is 503 `revocation_unavailable`. A mandate never outlives its passport or its parent, and a checkout passport lives 600 s, so request the three mandates within one passport's life.

## Mandate Capability Evidence

Send the result of the provider capability verifier (`verify_plural_pine_mandate_capability`) with the C6Z authority request. It is a top-level `mandate_capability_evidence` member beside `request` and `connector_evidence`. Grantex binds it into the signed `mandate_capability` artifact. The object is closed: unknown members are refused, and it must hold no secrets.

```json
{
  "schema_version": "oacp.mandate_capability_evidence.v1",
  "evidence_id": "<verifier evidence_id>",
  "tenant_id": "<request tenant_id>",
  "merchant_id": "<request merchant_id>",
  "provider": "plural_pine",
  "provider_environment": "sandbox",
  "result_status": "available",
  "external_validation_performed": true,
  "rails": ["plural", "upi_autopay"],
  "caps": [{ "rail": "upi_autopay", "max_amount": 1500000, "currency": "INR" }],
  "token_types": ["network_token", "upi_mandate"],
  "verified_at": "<checked_at>",
  "expires_at": "<checked_at + 6 h>",
  "redacted_evidence_ref": "provider:plural_pine:capability:<hash>:redacted",
  "evidence_hash": "<lowercase hex SHA-256 of the redacted provider response>"
}
```

The rules:

- `result_status` and `redacted_evidence_ref` are the verifier's own values.
- `rails` and `caps` use the mandate rail names `plural`, `upi_autopay` and `card_network_token`, with integer minor units.
- `verified_at` must be at most 6 h old and not in the future.
- `available` needs `external_validation_performed: true` and at least one rail.

The artifact then says `mandate_capability_status: "verified"`. It carries `mandate_capability_ref` (the redacted reference) and `mandate_capability_evidence`: the object without tenant and merchant, plus `evidence_object_hash`, Grantex's SHA-256 of the RFC 8785 form of what it received.

- Any other `result_status` gives `unavailable`.
- With no evidence the artifact says `unverified` and carries no reference. The placeholder `provider:mandate_rail:capability:pending:redacted` is gone.
- Malformed, stale, out-of-scope or placeholder evidence is refused as `mandate_capability_evidence_invalid` (422, recorded).
- The UCP profile emits checkout and order only while the live `mandate_capability` artifact is `verified`.

## Presence And Authentication Methods

A consent request names `presence`: `human_present` (the buyer confirms each cart with a passkey) or `human_not_present` (the buyer delegated purchases within the consented caps). The default is `human_not_present`. The buyer sees the mode on the consent page and it is part of the payload whose hash they approve. Approval records `amr: ["consent", "otp"]`. The Commerce Passport carries both as `presence` and `amr` claims, and mandates copy them. A passport issued before these claims existed reads as `human_not_present` with no methods. AgenticOrg's arbiter applies its stricter not-present rule set to `human_not_present`; neither mode adds a human step to a delegated purchase.
