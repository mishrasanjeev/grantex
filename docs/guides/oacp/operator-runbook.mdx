## Provision AgenticOrg Authority Access

1. Store `COMMERCE_C6Z_AUTHORITY_SERVICE_TOKEN` through the production secret path.
2. Add the AgenticOrg tenant id to `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS`.
3. Deploy or restart the Grantex auth service with both values available. `PUBLIC_BASE_URL` must be
   https (status list URIs are built from it).
4. Create the first OACP issuer key: `POST /v1/commerce/oacp/issuer-keys/rotate` with the platform
   admin key. Confirm its `kid` (`oacp-...`) appears in `GET /.well-known/jwks.json`.
5. Set `OACP_STATUS_LIST_PUBLIC_ENABLED=true` and restart when relying parties are ready to check
   status; until then they refuse artifacts with `revocation_status_unavailable`.
6. Submit a fixture `POST /v1/commerce/oacp/c6z/authority-requests` for that tenant.
   Public discovery stays disabled unless `OACP_PUBLIC_DISCOVERY_ISSUANCE_ENABLED=true` and the
   request opts in (`public_discovery_requested: true` with `namespace_attestation_ref` and
   `serving_host`); turn the flag on only after the owner approves publishing UCP profiles.
7. Confirm `artifact_count = 11`, or record the exact refusal/blocker.
8. To roll back, remove the tenant id from `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS` and rotate the token if there is any suspicion of exposure.

For a local stack (`PUBLIC_BASE_URL=http://localhost:<port>`), also set
`OACP_ALLOW_LOOPBACK_HTTP=true`; without it issuance refuses the http status list URI. It is
ignored when `NODE_ENV` is production. `OACP_AUTO_GENERATE_ISSUER_KEY=true` creates the first key
on first use in a local or test stack; it is also ignored in production. Then run the live
conformance suite from the in-tree build (the `oacp` suite is not yet in a published release of
`@grantex/conformance`):
`GRANTEX_CONFORMANCE_INTERNAL_TOKEN=<service token> node packages/conformance/dist/index.js --base-url http://localhost:<port> --api-key <developer key> --include oacp --suite oacp --oacp-issuer http://localhost:<port> --oacp-tenant <tenant>`.

## Production Turn-On Order

A merge to `main` deploys the auth service, so the OACP code is deployed before anything is
turned on. On 2026-10-20 production had no `oacp-` key in its JWKS and the status list route
was off. Turn OACP on in this order, and do not start a step before the previous one is
confirmed:

| Step | Action | Confirm | While this step is not done |
| --- | --- | --- | --- |
| 1. Service access | `COMMERCE_C6Z_AUTHORITY_SERVICE_TOKEN` (or `_SHA256`) from the secret manager and the AgenticOrg tenant ids in `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS`; redeploy. `PUBLIC_BASE_URL` is https. | A request with the token for an allow-listed tenant is not refused `403`. | Every service-token route answers `401` or `403`. |
| 2. First OACP issuer key | `POST /v1/commerce/oacp/issuer-keys/rotate` with the platform admin key. | `201 {kid, public_jwk, retired_kid: null}`; the `oacp-...` kid appears in `GET /.well-known/jwks.json` with `alg` `ES256`. | Every artifact, mandate and commitment-evidence issuance answers `503 oacp_issuer_key_unavailable`. |
| 3. Public status list | Set `OACP_STATUS_LIST_PUBLIC_ENABLED=true` (owner approval) and redeploy. | Issue one fixture authority request for an allow-listed tenant; its `status.status_list.uri` answers `200` with `application/statuslist+jwt`; an SDK verifier accepts one artifact against the production JWKS and list. | Issuance works and artifacts are signed, but `GET /status/oacp/:list` answers `401`, so every relying party, AgenticOrg included, refuses every artifact and mandate with `revocation_status_unavailable`. |
| 4. AgenticOrg | Point AgenticOrg at the Grantex issuer and JWKS, then turn on its own OACP flags by its runbooks. | AgenticOrg caches verified artifacts and records refusals with exact codes. | AgenticOrg has nothing it can verify; buyers get refusals, not invented facts. |
| 5. Optional surfaces | One at a time, each after owner approval: `OACP_PUBLIC_DISCOVERY_ISSUANCE_ENABLED`, `HTTP_SIGNATURE_DIRECTORY_ENABLED`, `REGISTRY_SCHEME_AGENT_IDS_ENABLED`, `AGENT_PASSPORT_KYA_TIER_ENABLED` (with `AGENT_PASSPORT_KYA_TIER_MAP`). | The matching checks below. | Public discovery is issued `disabled`; no directory, scheme ids or KYA tier are served. |

Rollback, in reverse: turning `OACP_STATUS_LIST_PUBLIC_ENABLED` off makes every relying party
refuse (fail closed), it does not make anything valid; revoking the issuer key withdraws
everything it signed; removing a tenant from the allowlist stops new issuance for it.

| Flag | Default | Effect when on |
| --- | --- | --- |
| `OACP_STATUS_LIST_PUBLIC_ENABLED` | off | Serves `GET /status/oacp/:list` unauthenticated (ttl 30 s, CORS `*`, rate limited). |
| `OACP_PUBLIC_DISCOVERY_ISSUANCE_ENABLED` | off | A C6Z request that opts in, from an allow-listed tenant, with both attestation members, gets `public_discovery_state` `enabled`. |
| `HTTP_SIGNATURE_DIRECTORY_ENABLED` | off | Serves `/.well-known/http-message-signatures-directory` with opted-in agents' keys, countersigned once by the platform key. |
| `REGISTRY_SCHEME_AGENT_IDS_ENABLED` | off | Agent attestations may carry `scheme_agent_ids`; lookup by scheme id; manifest lists them. |
| `AGENT_PASSPORT_KYA_TIER_ENABLED` | off | Agent Passports carry `kyaTier` from the operator's `AGENT_PASSPORT_KYA_TIER_MAP` (empty by default). |
| `OACP_AUTO_GENERATE_ISSUER_KEY` | off | Local and test only; ignored in production. |
| `OACP_ALLOW_LOOPBACK_HTTP` | off | Local only; ignored in production. |

Never put Shopify tokens, provider credentials, payment credentials, raw provider payloads, checkout links, raw POS callbacks, or webhook secrets in Grantex artifacts or logs.

## Keys and Revocation

| Task | Action |
| --- | --- |
| Rotate the issuer key (scheduled or after an incident) | `POST /v1/commerce/oacp/issuer-keys/rotate` (platform admin). The previous key retires and stays in the JWKS until its artifacts expire. |
| Key compromise | `POST /v1/commerce/oacp/issuer-keys/:kid/revoke`, then rotate. Every artifact the key signed stops verifying at once; ask AgenticOrg to refresh. |
| List keys | `GET /v1/commerce/oacp/issuer-keys` (no private material). |
| Revoke one artifact | `POST /v1/commerce/oacp/artifacts/:artifactId/revoke` with `{"reason_code": "..."}`. The status list shows INVALID within its 30 s ttl and a `revocation` artifact is issued. Revocation is final. |
| Audit what was issued or refused | `GET /v1/commerce/oacp/artifacts?tenant_id=...` or the `oacp_artifacts` table. |
| Revoke a mandate | `POST /v1/commerce/oacp/mandates/:jti/revoke` with `{"reason_code": "..."}`. It revokes the mandate and every mandate issued under it (an intent's carts, a cart's payments); their status list entries are INVALID within the 30 s ttl. Final, idempotent. |
| Suspend or reinstate a mandate | `POST /v1/commerce/oacp/mandates/:jti/suspend` with `{"reason_code": "..."}`, then `.../reinstate`. Platform admin, or the service token with `commerce.oacp.mandates.suspend`; tenant operators cannot. The status list entry is SUSPENDED (2) within its 30 s ttl and relying parties refuse `mandate_suspended`; the named mandate only, and nothing is issued under it (`parent_mandate_suspended`). Reversible; a suspended mandate can still be revoked, a revoked one cannot be reinstated. Audited (`oacp.mandate.suspended`, `oacp.mandate.reinstated`). |
| Suspend or reinstate an artifact | `POST /v1/commerce/oacp/artifacts/:artifactId/suspend` / `.../reinstate`, platform admin or `commerce.oacp.artifacts.suspend`. Relying parties refuse `artifact_suspended` while it lasts; `suspended_at` / `suspension_reason` show on reads. |
| Audit mandates | `commerce_audit_events` (`oacp.mandate.issued`, `oacp.mandate.refused`, `oacp.mandate.revoked`, `resource_type` `oacp_mandate`), written in the same transaction as the mandate row; and the `oacp_mandates` table: every issued, revoked and refused mandate (`refusal_code`, no token on refusals), `jwt_sha256` = AgenticOrg's `mandate_hash`, the passkey evidence of human-present carts. |
| Key compromise and mandates | Mandates are signed by the same OACP issuer key: revoking the key stops every mandate it signed (`issuer_key_untrusted`); AgenticOrg must request new ones. |

## Smoke Tests

```mermaid
flowchart TD
  start[Start] --> token[Verify service token and tenant allowlist]
  token --> config[Confirm AgenticOrg merchant config is tenant/merchant/seller scoped]
  config --> request[Submit fixture authority request]
  request --> artifact[Confirm 11 artifact families or expected blocker]
  artifact --> verify[Verify each JWS against the JWKS and its status list entry]
  verify --> adapters[Inspect adapter mapping payload]
  adapters --> cache[Ask AgenticOrg to cache and answer from source labels]
  cache --> purchase[Confirm purchase request returns handoff or blocker]
```

## Rollback

1. Remove the AgenticOrg tenant from `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS`.
2. Rotate the service token if compromise is suspected.
3. Ask AgenticOrg to stop refreshing artifacts and mark affected cache records stale.
4. Leave existing historical artifacts reviewable for audit/export (`oacp_artifacts`).
5. To invalidate artifacts already handed out, revoke them individually, or revoke the issuer key
   to invalidate everything it signed.
6. Publish an operator note with affected tenants, merchant ids, artifact families, and timestamps.

## Arbiter Decision Ledger

`POST /v1/commerce/oacp/arbiter-decisions` records every AgenticOrg arbiter decision in `commerce_arbiter_decisions` (migration `134_commerce_ledger.sql`), append-only: a trigger refuses `UPDATE`, `DELETE` and `TRUNCATE`, and a check constraint refuses a refusal row that carries a grant. It needs no new configuration: the service token and `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS` already provisioned for authority requests apply.

| Check | Evidence |
| --- | --- |
| An `allow` is countersigned | `201` with `decision_grant`; the token verifies against `/.well-known/jwks.json` and carries `approver_auth: "policy_arbiter"` |
| A `refuse` mints nothing | `201 {recorded: true}`; the row has `grant_jti IS NULL` |
| Replays are idempotent | the same body answers `200` with the same `jti`; another body answers `409 arbiter_decision_conflict` |
| Human approvals stay human | a `policy_arbiter` grant presented to `POST /v1/decisions/consume` is refused `400 malformed` |
| Tests | `npm --prefix apps/auth-service test -- commerce-oacp-arbiter-decisions.test.ts` |

To stop countersigning for a tenant, remove it from `COMMERCE_C6Z_AUTHORITY_SERVICE_TENANTS`; recorded decisions stay readable for audit.

## Witness Checkpoints

`POST /v1/audit/witness-checkpoints` stores AgenticOrg audit chain heads in `audit_witness_checkpoints` and refused forks in `audit_witness_forks` (both append-only, migration `134_commerce_ledger.sql`). It is authenticated with the AgenticOrg service token alone; no tenant allowlist applies, because `tenant_ref` names AgenticOrg's own tenant.

A row in `audit_witness_forks` means AgenticOrg presented a second, different hash for a chain position Grantex had already witnessed: treat it as an irregularity, open an incident with AgenticOrg, and keep both the witnessed countersignature and the fork record for the review. Read them with `GET /v1/audit/witness-checkpoints?source=agenticorg&tenant_ref=...`.

| Check | Evidence |
| --- | --- |
| Countersignature verifies | header `typ` `audit-witness+jwt`, `kid` in `/.well-known/jwks.json` |
| Replay is idempotent | the same head answers `200` with the same `witness_id` |
| Fork is refused | another hash at a witnessed `head_seq` answers `409 WITNESS_FORK` and adds a fork row |
| Tests | `npm --prefix apps/auth-service test -- audit-witness-checkpoints.test.ts` |

## Wallet Ledger Chain

Migration `134_commerce_ledger.sql` adds `chain_seq`, `prev_hash` and `entry_hash` to `wallet_ledger_entries`, chains every new entry in a `BEFORE INSERT` trigger under a per-wallet advisory lock, and backfills existing entries per wallet in `(created_at, id)` order. The backfill disables the table's append-only trigger only inside the migration transaction, which already holds an exclusive lock on the table; it is enabled again before commit. Plan the migration for a maintenance window on a large ledger. No flag: the columns and trigger are additive and no existing response changes.

| Check | Evidence |
| --- | --- |
| A wallet's chain is intact | `GET /v1/admin/prepaid-wallets/{walletId}/ledger/verification` with the admin credential answers `valid: true` |
| Tampering is found | `valid: false` lists each `entry_hash_mismatch` (edited), `prev_hash_mismatch` / `chain_seq_mismatch` (deleted, inserted or reordered) entry |
| Tests | `npm --prefix apps/auth-service test -- wallet-ledger-chain.test.ts` and, with `AUDIT_INTEGRATION_DATABASE_URL`, `commerce-ledger-postgres.integration.test.ts` |

A failed verification is an irregularity in financial evidence: block the wallet, keep a database snapshot, and reconcile from backups before any repair. Never repair a ledger by editing or deleting entries.

## Protocol Surfaces, Receipts And Network Identity

These routes ship enabled behind authentication (the service token with its route scope and the tenant allowlist, an operator of the tenant, or the platform admin) and need no new configuration. All of them depend on step 2 (issuer key); relying parties depend on step 3.

| Check | Evidence |
| --- | --- |
| UCP profile | `GET /v1/commerce/oacp/ucp-profile?tenant_id&merchant_id&seller_agent_id&served=...` lists only served capabilities whose backing artifacts are live; checkout and order are withheld (`mandate_capability_unverified`) until a `mandate_capability` artifact is `verified`; `publication_allowed` stays false unless public discovery was issued `enabled`. Tests: `commerce-ucp-profile.test.ts`, `commerce-c6z-public-discovery.test.ts`. |
| ACP allowance | `POST /v1/commerce/oacp/acp/delegate-payment-allowance` refuses card data (`422 card_data_refused`) and amounts over the passport cap; each issue and refusal is a `commerce_audit_events` row. Test: `commerce-acp-delegate-payment.test.ts`. |
| ACP order events | `GET /v1/commerce/oacp/acp/orders/{order_id}/event` returns data only for existing `commerce_orders` rows; Grantex sends no webhooks. Test: `commerce-acp-order-events.test.ts`. |
| Settlement receipts | `POST /v1/commerce/oacp/commitment-evidence/settlement-receipts` (service token only, scope `commerce.oacp.commitment_evidence.write`) issues a signed `commitment_evidence` artifact recording the receipt as reported, not verified. Test: `commerce-settlement-receipt-evidence.test.ts`. |
| Key directory | With `HTTP_SIGNATURE_DIRECTORY_ENABLED`, `/.well-known/http-message-signatures-directory` lists only agents whose developer opted in (`PUT /v1/agents/:id/http-signature-directory`). Its countersignature is the registry's, not each key's, so strict Web Bot Auth clients ignore the keys. Test: `http-signature-directory.test.ts`. |

## Refusal Copy

Use exact blockers: missing source evidence, stale artifact, unsafe executable request, provider capability missing, tenant not allowlisted, or authority temporarily unavailable.
