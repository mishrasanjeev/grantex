## Overview

Grantex budget controls let you allocate a monetary budget to any grant, debit amounts on each API call, and receive real-time alerts when spending thresholds are crossed.

Key features:
- **Per-grant budget allocation** with atomic debit operations
- **Race-condition safe** — uses SQL `WHERE remaining_budget >= amount`
- **Threshold alerts** at 50% and 80% via event bus (`budget.threshold`)
- **Exhaustion events** when the budget hits zero (`budget.exhausted`)
- **JWT `bdg` claim** — budget balance embedded in grant tokens for downstream enforcement

## Allocating a Budget

<CodeGroup>

```typescript TypeScript
const grantex = new Grantex({ apiKey: 'gx_...' });

const allocation = await grantex.budgets.allocate({
  grantId: 'grnt_01HXYZ...',
  initialBudget: 100,
  currency: 'USD', // optional, defaults to USD
});

console.log(allocation.id);             // "bdg_01HXYZ..."
console.log(allocation.remainingBudget); // "100.0000"
```

```python Python
from grantex import Grantex, AllocateBudgetParams

grantex = Grantex(api_key="gx_...")

allocation = grantex.budgets.allocate(AllocateBudgetParams(
    grant_id="grnt_01HXYZ...",
    initial_budget=100,
    currency="USD",
))

print(allocation.remaining_budget)  # "100.0000"
```

```bash cURL
curl -X POST https://api.grantex.dev/v1/budget/allocate \
  -H "Authorization: Bearer gx_..." \
  -H "Content-Type: application/json" \
  -d '{"grantId": "grnt_01HXYZ...", "initialBudget": 100}'
```

</CodeGroup>

## Debiting from a Budget

Each debit atomically decrements the remaining balance. If the debit exceeds the remaining budget, the API returns **402 Payment Required** with code `INSUFFICIENT_BUDGET`.

<CodeGroup>

```typescript TypeScript
const result = await grantex.budgets.debit({
  grantId: 'grnt_01HXYZ...',
  amount: 0.50,
  description: 'GPT-4 API call',
  metadata: { model: 'gpt-4', tokens: 1200 },
});

console.log(result.remaining);      // "99.5000"
console.log(result.transactionId);  // "btx_01HXYZ..."
```

```python Python
from grantex import DebitBudgetParams

result = grantex.budgets.debit(DebitBudgetParams(
    grant_id="grnt_01HXYZ...",
    amount=0.50,
    description="GPT-4 API call",
))

print(result.remaining)  # "99.5000"
```

</CodeGroup>

### Retrying a Debit Safely

The current SDK source sends a fresh `Idempotency-Key` for each debit call and
reuses it across that call's automatic retries. Supply your own 16-256 character
key when retrying the same operation across separate SDK calls. This source
change does not itself publish a new SDK package.

Server replay protection requires migration `139_budget_debit_idempotency.sql`
and `BUDGET_DEBIT_IDEMPOTENCY_ENABLED=true`. The flag defaults off. With it on:

- The key is scoped to the authenticated developer and grant; only its SHA-256
  hash is stored. The response and financial writes commit atomically.
- A matching retry within 24 hours returns the original `remaining`,
  `transactionId` and `grantId`, even if later operations changed the balance.
  It does not create a ledger entry or emit another threshold event.
- Changed amount, description or metadata returns `409 IDEMPOTENCY_CONFLICT`.
  Object-key order does not matter; array order does. Omitted descriptions and
  metadata are treated as `null` and `{}` respectively.
- Revoked or expired grants remain denied. Another tenant cannot read or replay
  the response. Concurrent matching requests produce one debit.
- After 24 hours the key can identify a new operation. Never blindly retry an
  uncertain debit after that window: reconcile its transaction before deciding
  whether to submit a fresh operation. Use a fresh key for each new operation.
- Expired reply state for a grant is removed during its next successful keyed
  debit. Inactive grants may retain expired hashes until that happens or their
  grant/ledger data is removed; expiry is a replay deadline, not a claim that a
  background retention worker has deleted every row. Ledger history is retained.

With the flag off, or without the header, the existing behavior is unchanged
and automatic retries can still debit more than once. Do not assume a key alone
provides protection on an older or unconfigured server.

### Replay Rollout and Rollback

1. Back up the database and verify restore, then deploy the complete migration
   set through `139`. This adds a new table and indexes only; no allocation or
   transaction backfill is required. Keep the flag off during code rollout.
2. Require the local real-Postgres retry, concurrency, rollback, tenant and expiry
   tests, SDK socket-failure E2E and all normal release/security gates to pass.
   Verify the exact deployed image and migration before approving activation.
3. Obtain explicit operator approval for activation. Keep the setting consistent
   on every serving instance; a mixture of enabled and disabled instances is not
   a safe replay service. Existing customer flags and credentials are not changed
   by deploying the default-off code.
4. Before activation, the previous image remains schema-compatible. After any
   keyed request has been accepted, do not blindly turn the flag off or send
   retries to an older image that ignores keys. Preserve replay rows and ledger
   history and use a deduplication-capable revision or an explicitly approved
   write-drain/reconciliation plan. Never drop replay state to make a rollback
   appear successful.

### Handling Insufficient Budget

```typescript
try {
  await grantex.budgets.debit({ grantId, amount: 9999 });
} catch (err) {
  if (err instanceof GrantexApiError && err.code === 'INSUFFICIENT_BUDGET') {
    // Balance too low — prompt user to top up
  }
}
```

## Budget JWT Claim

When a grant has a budget allocation, the issued grant token includes a `bdg` claim with the current remaining balance at the time of token issuance:

```json
{
  "sub": "user_123",
  "agt": "did:grantex:agent_abc",
  "scp": ["read:email", "send:email"],
  "grnt": "grnt_01HXYZ...",
  "bdg": 99.5,
  "exp": 1709312000
}
```

Service providers can use this claim to enforce budget limits without making additional API calls.

## Threshold Alerts

Grantex automatically emits events when spending crosses thresholds:

| Event | Trigger |
|---|---|
| `budget.threshold` | Remaining budget drops below 50% or 20% of initial |
| `budget.exhausted` | Remaining budget reaches zero |

These events are delivered via:
- **Webhooks** — to all registered webhook endpoints
- **SSE/WebSocket** — via the real-time event stream (`GET /v1/events/stream`)

Example event payload:

```json
{
  "id": "evt_01HXYZ...",
  "type": "budget.threshold",
  "createdAt": "2026-03-01T12:00:00Z",
  "data": {
    "grantId": "grnt_01HXYZ...",
    "remainingBudget": "20.0000",
    "initialBudget": "100.0000",
    "thresholdPercent": 80
  }
}
```

## Portal Dashboard

Budget allocations are visible in the developer portal under **Budgets**:
- Summary cards showing total allocated, spent, and remaining
- Per-grant usage bars with status badges (Healthy / > 50% / > 80% / Exhausted)
- Transaction drill-down with pagination

## API Reference

| Method | Path | Description |
|---|---|---|
| `POST` | `/v1/budget/allocate` | Create a budget allocation for a grant |
| `POST` | `/v1/budget/debit` | Debit an amount from a grant's budget |
| `GET` | `/v1/budget/balance/:grantId` | Get current budget balance |
| `GET` | `/v1/budget/transactions/:grantId` | List paginated transaction history |
