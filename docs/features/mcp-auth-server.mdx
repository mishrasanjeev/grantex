## Release and installation

The registry baseline during preparation is `@grantex/mcp-auth@2.0.2`;
its [historical limitations](/legacy/mcp-auth-server-2) still apply to that
immutable version. The instructions below describe version 3.

`@grantex/mcp-auth@3.0.0` is the release candidate for this deployment profile.
Check [Release Status](/release-status) for registry verification before
installing. Node.js 22.12+ and `@grantex/sdk` 0.8+ are required.

```bash
npm install @grantex/mcp-auth@3.0.0 @grantex/sdk@0.8.0 pg
```

Version 3 is a breaking upgrade from 2.0.2, not an assertion that every MCP
client or deployment has been independently certified. Follow the
[complete deployment and consent guide](/mcp-auth) and
[enforcement migration](/migration-enforcement).

## Request flow

1. The protected MCP resource advertises resource metadata in its HTTP 401 challenge.
2. The client discovers authorization metadata and starts authorization with PKCE S256 and the intended resource.
3. The server validates client identity, redirects and resource, then renders the consent page.
4. Approval starts Grantex authorization with audience and purpose; live-mode Grantex still requires the principal's passkey.
5. The callback requires the bound browser cookie before issuing a single-use authorization code.
6. Token exchange validates PKCE and the resource, exchanges the upstream code and returns an audience-bound token.
7. The resource guard checks signature, issuer, audience, scopes and configured revocation before execution. Sensitive tools can require consumed decision grants.

## Deployment choices

| Concern | Version 3 behavior | Operator responsibility |
|---|---|---|
| Shared state | Postgres and Redis adapters for clients, codes, consent, refresh bindings and revocations | Provision drivers/storage, apply migrations, share state across replicas |
| Memory storage | Available for evaluation | Do not horizontally scale process-local state |
| Consent | Rendered, CSRF-protected page and browser-bound callback | Configure trustworthy labels/purpose and test the principal handoff |
| Resource binding | Resource indicators and expected audience | Pin the canonical HTTPS resource and issuer |
| Revocation | Guard/middleware requires a checker or explicit `none` | Connect the authorization server's revocation storage; never describe `none` as enforcement |
| Tool enforcement | Refuses unauthorized tool calls at the resource | Configure manifests, scopes and trusted decision verification/consumption |
| Refresh | Durable bindings and rotation | Protect state and test restart/replay behavior |

The [deployment guide](/mcp-auth) includes executable Postgres/Redis examples,
purging expired rows, issuer/resource settings, lifecycle hooks, consent-page
customization, tool policy and migration from 2.x.

## Explicit revocation configuration

`createMcpResourceGuard`, Express `requireMcpAuth` and Hono `requireMcpAuth`
refuse startup without `revocations`. Supply an object implementing
`isTokenRevoked(jti)` from the same shared storage used by the authorization
server. Storage failures must deny, not silently authorize.

`revocations: 'none'` is an explicit warned opt-out. It does not query grant
status and accepts otherwise valid revoked tokens until expiry. Local JWT
verification alone is not current-state authorization.

## Tests and boundaries

The package has unit/conformance tests, real Postgres/Redis integration tests
including a server restart, and Chromium consent-page/accessibility tests.
Test your own client, TLS origin, reverse proxy, storage failover and principal
passkey handoff before enabling production traffic.

The local token revocation checker concerns tokens recorded in its storage;
it is not a substitute for every upstream grant/ancestor-state check. Keep
Grantex service-side enforcement for agent-specific authority. The consent
page does not independently prove principal identity or replace live WebAuthn.

For the six limitations of the previous package, see
[the historical 2.0.2 guide](/legacy/mcp-auth-server-2). Those warnings must not
be mistaken for version 3 deployment instructions.
