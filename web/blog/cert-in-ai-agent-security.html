The problem is ordinary access, at agent speed.

CERT-In's Critical Advisory CIAD-2026-0049, issued on 15 October 2026, describes agents reaching systems beyond their assigned tasks. Exposed credentials, excessive permissions and reachable APIs gave them a way in.

A prompt saying "only read this case" is not a security control. The service receiving the request must enforce the limit.

Grantex handles delegated authorization: who allowed an agent to do what, until when, and whether that permission still stands. That limited permission is called a grant. Your application still enforces which records the agent can access.

Grantex supports parts of the advisory's recommendations. It is not a CERT-In certification, endorsement or complete compliance solution. These workflows are integration patterns, not evidence that every deployment has the controls enabled.

01 / LIMIT THE JOB

Read this case. Not the whole business.

A merchant-review agent needs to read a case and prepare a summary. Give it limited, expiring authority instead of a reusable administrator key. Request a separate grant for each run; this is a runtime integration choice, not automatic process isolation.

In practice: cases:read does not itself mean "only case C-1042." The service must bind access to the authenticated tenant and permitted case. A scope label alone does not prevent bulk export.

A trusted gateway can redeem a vault credential reference and inject the upstream key without giving it to the agent. This helps only if the agent cannot read that key elsewhere or bypass the gateway.

02 / SEPARATE PREPARATION FROM APPROVAL

Preparing a payment is not permission to send it.

An agent can assemble evidence and draft a recommendation. A sensitive operation needs a separate, authenticated human decision and a final check by the system that executes it.

See the related payment guidance in CIAD-2026-0046. This is an illustrative design, not a live merchant-activation claim. The merchant pilot remains sandbox-only.

03 / CONTAIN AND INVESTIGATE

Stop access without asking the agent to cooperate.

If an agent starts requesting unrelated records, an independently protected operator path should be able to withdraw its authority.

Revoking a Grantex grant does not revoke a stolen upstream API key. Rotate that key at its issuer and close direct access paths. Hash-linked audit records help check evidence integrity; they do not make storage undeletable.

BE CLEAR ABOUT WHAT IS ENABLED

Available does not mean configured.

  • EXISTING PRODUCT MECHANISMSGrants, delegation, revocation, current-authority verification, decision grants, vault references and audit records. Each requires correct integration and configuration; availability is not a test result for your application.
  • NEWER OPT-IN SOURCE CONTROLSRestricted gateway origins, redirect refusal, TypeScript rejectRedirects and Helm network policy. Local synthetic gateway tests and chart checks passed. These additions are not in a published SDK release; no enforcing Kubernetes CNI was tested. Check release status for installed packages.
  • DEPLOYMENT AND ORGANISATION CONTROLSTenant-owned SSO/MFA, network enforcement, secret rotation, alert routing, log jurisdiction/retention, patching and incident response. Installing Grantex does not complete these. A Helm policy does not automatically protect Cloud Run or every agent worker.
A USEFUL FIRST PILOT

Prove five things before widening access.

  1. The intended read succeeds. Return only permitted tenant and case data.
  2. A broader action fails. Try another tenant, bulk export and an unapproved write.
  3. Missing or changed approval fails. A changed beneficiary or amount cannot reuse an earlier decision.
  4. A disallowed destination fails. Test the actual network boundary and a redirect.
  5. A revoked grant fails on the next check. Confirm an operator receives the alert and can retrieve evidence.

Use synthetic records, no live financial effects, and record the revision, effective settings, results and responsible owner. An untested control stays open.
